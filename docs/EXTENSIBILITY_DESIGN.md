# AttaCore 扩展面设计

> `EXTENSIBILITY_DESIGN.md` · 版本 v0.1 · 2026-08-29
> 目的：把 AttaCore 从「一个可配置的 agent 引擎」变成「一个可二次开发的 agent 内核」。
> 这份文档描述的是**目标形态与理由**。派生出的工单是迁移进度跟踪，按开发约定 §2 不入库（落在 `.local/`）；本文档不依赖它们存在。
> 想知道**现在**能接什么，看 [extension_points.md](extension_points.md) —— 那是二开者的入口，且由代码生成、有测试保证不漂移。

### 0.2 关于「现状」的重要警告

**§7 以及 §3 各表「现状」一列的判断，来自对公开仓库的通读，不是对工作副本的核实。** 附录 B 列出了已知未核实的项。仓库自带的插件设计文档至少有一处（场景解析闭集）已经过时——代码已修复而文档未更新，说明这类偏差真实存在。

因此：

> **实施者的第一项工作是核实，不是修改。** 动任何代码之前，逐条比对本文档的现状判断与实际代码，产出差异报告并停下等待确认。工单 `P0-1` 就是这件事。
>
> **凡文档与代码不一致，以代码为准，并回头修正本文档。** 不要按文档描述去「修复」一个代码里其实已经正确的地方。

### 0.3 三部分的顺序是刻意的

1. **§1–§5 目标扩展面** —— 不受现有实现约束的最佳设计。回答「一个可嵌入的 Rust agent 内核，应该开放哪些扩展点、每个点长什么样、哪些永远不开」。读这部分时请忘记现在的代码。
2. **§6 与 DSH 的对照** —— 拿业界最完整的插件化 harness 做标尺，逐域比对，标出我们该抄的、该拒绝的、以及我们已经更强的。
3. **§7–§8 现状差距与迁移策略** —— 现有实现距离目标有多远，怎么分阶段走过去。**只有这部分讨论现状。**

**一句话概括当前形状**：AttaCore 的扩展面**宽在边缘、窄在中心**——模型、工具、场景、hook、MCP、插件都已是 trait 或配置驱动，但主循环、权限管线、记忆、执行层、会话投影全是具体类型。目标是把中心也打开，**但打开的方式与边缘不同**：中心开放的是「决策」，不是「实现」。

## 1. 设计原则

**原则 1 · 内核开放决策，边缘开放实现。**
边缘（模型协议、工具、场景）二开者需要**换掉整个实现**；中心（循环、压缩、权限）二开者需要的是**改判断**，不是重写流程。把中心也做成「可替换实现」，等于把不变量和可测试性一起交出去。

**原则 2 · 一切皆插件，除了边界。**
以下永远不作为扩展点暴露：能力授权与模块解析、权限规则求值顺序、资源限额与中断、调度器与配额记账、沙箱策略的决定权、会话日志的 append-only 语义、循环骨架的步骤顺序。清单见 §5。

**原则 3 · 沙箱的策略不可插拔，后端可以。**
这一条需要精确表述，此前的粗略说法「沙箱不可插拔」会误导。**决定"这次执行受不受约束、受什么约束"的是内核；实现"如何约束"的后端可以替换。** 契约形如 `confine(argv, policy) -> ConfinedArgv`：`policy` 由内核给定，后端只负责兑现，且**永不允许静默降级为无约束**。

**原则 4 · 扩展点是承诺，数量必须可数。**
每开一个扩展点就是一个永久契约。宁可少开、后补，不可先铺开再收回。插件对内核的贡献点必须保持在可以逐一枚举的规模——这也是「整个插件子系统可编译期切掉」这个能力的前提。

**原则 5 · 信任级决定能力，不由插件自称。**
同一个扩展点，**自写的代码**和**下载来的代码**能做的事不一样。典型：改写工具入参、改写系统提示词、写持久事件——这些自写脚本可以做，下载插件不可以，或必须经安装期披露。判据是来源，不是声明。

**原则 6 · 高频路径默认原生。**
按调用频次给扩展点分级。~10⁰–10¹ 次/轮的点位随便写；~10²–10³ 次/轮的点位（流式 chunk）默认不暴露给脚本，只提供声明式规则或显式 opt-in 且计入配额。

## 2. 扩展的四种形态

所有扩展点归入四类。这个分类决定了成本、风险和适用载体，全文按此标注。

| 型 | 名称 | 形态 | 谁用 | 风险 |
|---|---|---|---|---|
| **A** | **替换实现**（Provider） | 一个 trait，宿主或插件提供实现，内核持 `Arc<dyn T>` | 嵌入方、深度定制者 | 中——契约一旦公开难改 |
| **B** | **注册贡献**（Contribution） | 往注册表里加东西，返回 disposer 可撤销 | 插件、场景包 | 低 |
| **C** | **点位拦截**（Hook） | 在流程某点观察 / 否决 / 改写 | 用户脚本、插件 | 高频点位有性能风险；改写权限需按信任分级 |
| **D** | **声明配置**（Config） | 不写代码，改文件即可 | 所有人 | 最低 |

**二开能力的强弱，看的是这四类的覆盖面是否均衡。** 只有 A 没有 C，二开者要改一点行为就得重写整个 provider；只有 C 没有 A，就永远换不掉底层。目前的短板集中在 **C（点位太少、能力太弱）** 和**中心域的 A（根本没有 trait）**。

## 4. 关键契约草案

只列需要新设计或需要重画的。已经存在且形状正确的（`Model`、`Tool`、`AgentScene`、`Permission`、`AutoClassifier`、`PluginResolver`）不重复。

### 4.1 提示词装配（P1–P4）

现在的形态是「场景一次性返回一个块列表」，二开者要改其中一块只能重写整个场景。目标形态是**注册 + 装配点位**：

```rust
/// 提示块：有序、具名、可撤销。name 是二开者定位它的唯一手段。
pub struct PromptBlock {
    pub name: String,            // "scene.skeleton" / "skills.catalog" / "memory.session"
    pub role: BlockRole,
    pub order: i32,              // 升序拼接，留出负数与大间隔给插件
    pub content: PromptContent,  // Static(String) | Provider(Arc<dyn Fn>)
    pub cache_hint: Option<CacheHint>,
    pub origin: Origin,          // Kernel | Scene | Plugin(name) | Script(path)
}

pub trait PromptRegistry {
    fn block(&self, b: PromptBlock) -> Disposer;
    fn context(&self, name: &str, order: i32, p: ContextProvider) -> Disposer;
    fn variable(&self, name: &str, p: VariableProvider) -> Disposer;  // {{name}} 插值
}

/// 装配点位：waterfall，可增、删、改、重排。
/// 拿到的是完整的块列表，返回值即最终结果。
/// 下载来的插件默认只能"加"，改和删需要显式能力 + 安装期披露。
fn on_prompt_assemble(asm: &mut PromptAssembly, ctx: &AssembleContext, next: Next) -> Result<()>;
```

两个设计决定：

- **`name` 是契约的一部分，不是注释。** 二开者按名字找到「技能清单那一块」才能改它。没有稳定命名，装配点位就只是一个不透明字符串列表，什么也做不了。内核块的命名应当成为公开契约并遵守语义化演进。
- **`origin` 必须携带并可被点位读取。** 这样才能实现「插件不能删除内核块」「场景块优先于插件块」这类规则，也是审计的基础。

### 4.2 工具环绕包装（T5）

超时、重试、指标、缓存、幂等去重——这些是**横切关注点**，既不属于工具实现，也不属于权限判断。缺了这个点位，它们只能被硬编码进循环。

```rust
/// 环绕整个工具分发。可替换 signal（施加更严的超时），
/// 可短路（缓存命中直接返回），可重试（多次调用 next）。
/// 不可改写入参——改参属于 T4，受信任级约束。
async fn around_tool_dispatch(
    call: &ToolCall,
    exec: &mut ToolExec,
    next: NextDispatch<'_>,
) -> ToolOutcome;
```

### 4.3 会话事件扩展（S2）

「状态即日志」这条原则，如果日志本身是闭合枚举，二开者的状态就只能藏在别处——正好违反原则。目标形态是给扩展留一个带命名空间的变体：

```rust
pub enum LogEntry {
    // ... 内核变体 ...
    /// 扩展事件。ns 由插件名或脚本路径决定，内核不解释 payload，
    /// 但保证顺序、持久化与重放；投影器（S3）决定它是否模型可见。
    Extension { ns: String, kind: String, payload: serde_json::Value },
}
```

配套两条不变量：

- **模型可见即入日志。** 扩展事件若被投影为模型可见内容，必须能从日志完整重建。
- **未知 `ns` 必须可跳过。** 卸载插件后旧日志仍能加载，未知扩展事件降级为惰性记录，不阻断重放。

### 4.4 轮次策略（L1）

不把循环做成可替换 seam，而是把**决策**从骨架里提出来。骨架的步骤顺序仍然硬编码。

```rust
/// 纯决策，无 I/O。所有输入都是内核算好的事实，输出是指令。
/// 这使它天然适合脚本载体：CPU 占比≈0、改动频繁、易于测试。
pub trait TurnPolicy: Send + Sync {
    /// 本轮开始前：要不要先压缩？压到什么程度？
    fn before_step(&self, s: &TurnState) -> StepDecision;   // Proceed | Compact(..) | Stop(reason)

    /// 模型调用失败后：重试、换模型、压缩后重试、还是放弃？
    fn on_model_error(&self, e: &ModelErrorFacts, s: &TurnState) -> Recovery;

    /// 一步结束后：继续、停止、还是等待外部输入？
    fn after_step(&self, s: &TurnState) -> Continuation;
}
```

覆盖「何时停、怎么退、何时压」——这是九成「想改循环」诉求的实际内容。真要改**循环形状**（树搜索、辩论、回溯投票）的，仍然让他 fork，那条边界不动。

### 4.5 执行层（X1–X5）

四个 trait 一组，一起换才有意义（换了子进程不换文件系统，等于半个远端）：

```rust
pub trait Subprocess { async fn spawn(&self, spec: ProcSpec) -> Result<ProcHandle>; }
pub trait FileSystem { /* read / write / list / stat / watch，全部路径受策略约束 */ }
pub trait Shell      { async fn run(&self, cmd: ShellCmd) -> Result<ShellOutcome>; }
pub trait Terminal   { async fn open(&self, spec: PtySpec) -> Result<PtyHandle>; }

/// 沙箱后端：只负责"如何约束"，policy 由内核给定。
pub trait SandboxBackend {
    fn confine(&self, argv: &[String], policy: &SandboxPolicy) -> Result<ConfinedArgv>;
}
pub struct ConfinedArgv {
    pub argv: Vec<String>,
    /// 诚实报告：Full = 兑现了策略的全部承诺；Partial = 平台能力不足，
    /// 需要绝对边界的消费者必须拒绝。
    pub enforcement: Enforcement,
    pub denial_signatures: Vec<String>,
}
```

**硬约束：受约束的策略绝不允许静默降级为无约束执行。** 没有可用后端时报错，不是放行。

### 4.6 宿主集成（H1–H2）

```rust
/// 事件出口。嵌入方拿这个把 agent 的事件接进自己的世界。
/// 必须是同步非阻塞的投递语义，慢消费者由内核缓冲/丢弃策略处理，
/// 绝不允许一个慢 sink 卡住轮次。
pub trait EventSink: Send + Sync {
    fn emit(&self, ev: &AgentEvent);
}

/// 人机交互的唯一出口：授权、澄清、选择、确认。
/// 无实现时的默认行为必须是"拒绝"而不是"通过"。
#[async_trait]
pub trait Elicitation: Send + Sync {
    async fn ask(&self, req: ElicitRequest) -> ElicitOutcome;
}
```

`EventSink` 的缺失是目前嵌入体验最直接的缺口——上层要拦截事件流，只能绕到更外层去做。

### 4.7 插件装载（D2）

wasm 与 JS 两种载体应当共用一个装载契约，差异下沉到实现：

```rust
pub trait PluginLoader: Send + Sync {
    fn kind(&self) -> LoaderKind;                       // Wasm | Script | Native
    fn load(&self, m: &PluginManifest, caps: &ResolvedCapabilities) -> Result<LoadedPlugin>;
}
```

**四条不变量适用于所有载体**（详见后续的插件开发文档）：

1. **单一授权点** —— 所有载体共用同一张能力表与同一个授权函数，不是两套白名单。
2. **载体之间不直接互操作** —— 只通过宿主契约通信，不建跨内存模型的 FFI 层。
3. **载体是编译期 feature** —— 不同时链入所有载体，边缘构建可以只带一个。
4. **披露适用于所有载体** —— 凡是模型可见的文本（工具描述、场景提示词、注入的提示块），下载来的一律过安装期披露；自写的不需要。

## 5. 内核清单：永远不开放的 11 项

| # | 项 | 为什么不能开 |
|---|---|---|
| 1 | 能力授权与模块解析 | 决定 `import 'host:fs'` 成不成立的那个函数。可替换 = 无授权 |
| 2 | 权限规则求值顺序 | 8 阶段的顺序本身是安全属性（例如工具自判 Allow 必须后置于 deny 规则与路径检查） |
| 3 | 资源限额与中断 | 失控插件的唯一止损手段 |
| 4 | 调度器与配额记账 | 记账可替换 = 配额可绕过 |
| 5 | 沙箱策略与是否施加 | 后端可换，**决定权不可换**（原则 3） |
| 6 | 会话日志 append-only 语义与不变量校验 | 「模型可见即入日志」靠运行期断言保证，断言可替换 = 原则失效 |
| 7 | 循环骨架的步骤顺序 | 步骤顺序是所有不变量的载体；决策已由 L1 开放 |
| 8 | 安装期披露 | 「只警告的限制，每个自动安装器都会一步跨过去」 |
| 9 | 权限规则来源优先级 | 插件规则必须永远低于用户设置与组织策略 |
| 10 | 场景合成 / 继承 | 组合面指数增长，且与「一会话一场景」的重放不变量冲突 |
| 11 | 插件贡献点的数量上限 | 可编译期切掉插件子系统，依赖贡献点保持可数 |

> 前 6 项不仅是安全需要，它们本身就是这个内核相对通用框架的差异化。做成可替换的，等于把核心竞争力交出去。

## 6. 与 DSH 的对照

DSH（DeepSeek Harness，Node + Cordis）是目前插件化做得最彻底的 agent harness，把它当标尺。它的能力接缝表把每个 `ctx.*` 键分为 **core（不可换）/ seam（可换）/ bundle**，共 60 余项。

### 6.1 逐域对照

| 域 | DSH | AttaCore 现状 | 判定 |
|---|---|---|---|
| LLM 适配 | `ctx.llm` **seam**，3 实现 | trait 干净（2 方法），2 真实现 + 任务路由；**但构造工厂是闭合 match** | 开工厂注册表（M2） |
| 模型路由 | `ctx.agentDefaultModel` core | 任务级路由 + 配置驱动 | **我们更强**，保持 |
| 系统提示词 | `ctx.systemPrompt` core，但有 `section/context/variable` 注册 + `assemble` waterfall | 场景一次性返回块列表 + 追加/覆盖配置 | **抄**（P1–P4）——差距最大处 |
| 工具注册 | `ctx.tools` core，`register()` 返回 disposer，支持作用域与遮蔽 | 可加、可替换、可装饰，**不可移除**；内建集是固定序列 | 补 disposer 与 remove（T2） |
| 工具执行管线 | 8 阶段，含 **around-dispatch waterfall** | 前后各一个点位 + 8 阶段权限管线；**无环绕点位** | **抄环绕点位**（T5） |
| 权限 | `ctx.approval` seam + 单调 guard（无 allow 结果） | 决策器可换 + 分类器两实现 + **8 级来源优先级 + 按来源整批撤销 + 十种决策理由** | **我们更强**，保持 |
| 沙箱 | `ctx.sandbox` seam，`confine(argv, policy)`，多平台后端在一个 provider 内，**诚实报告 full/partial** | 分散在工具与能力声明中 | 抄**形状与诚实报告**，不抄"策略可插拔"（X5/X6） |
| 会话日志 | `ctx.sessions` core + `ctx.sessionPersistence` **seam（两实现）**，事件表**可声明合并扩展** | 存储 trait 在但唯一实现；事件是**闭合枚举** | **抄事件扩展**（S2）——第二大差距 |
| 上下文压缩 | `ctx.compaction` seam + 独立的结果裁剪 core | trait 存在，**但触发与多数策略绕过 trait 直接调具体函数** | 重构使 trait 真正在热路径（C1–C3） |
| 主循环 | `ctx.agentLoop` **bundle，可换** | 硬编码线性循环，恢复分支是 match 臂 | **不抄可换 seam**，改为策略外移（L1） |
| 子 agent | `ctx.subagents` seam，**6 个实现** | trait 在，一个真实现 | 补第二实现验证契约（L3） |
| 执行层 | `subprocess`/`shell`/`fs`/`terminals` **全是 seam**，本地/沙箱/远端多实现 | **无抽象层**，具体工具直连系统调用 | **抄**（X1–X5）——最大空白 |
| 技能 | `ctx.skills` seam（两实现） | 具体管理器，仅文件系统 | 低优先级（K1） |
| 记忆 | 无直接对应 | 具体结构体 + 固定目录布局 | **开**（R1–R4） |
| 事件出口 | `session/event` 广播 + 事件树 | 固定 mpsc，**无出口 trait** | **开**（H1） |
| 配置 | **4 层 YAML patch 合成** + schema 校验 + 生成目录 | 三层合并 + JSON Schema（**hook 配置在 schema 里无类型**） | **不抄 4 层**；类型化 hook 配置 |
| MCP | 无（走子进程 seam） | **5 种 transport 配置驱动，含进程内注册** | **我们更强** |
| 插件宿主 | 无（框架本身即是） | 单一 trait、少量贡献点、**整个子系统可编译期切掉** | **我们更强**，保持 |

### 6.2 该抄的五条

1. **会话事件表可扩展** —— 否则「状态即日志」对二开者不成立
2. **提示词的注册 + 装配点位** —— 「在各环节写自己的提示词」的标准答案
3. **工具环绕点位** —— 横切关注点的正确位置
4. **注册返回 disposer** —— 卸载才干净，不必靠 deny 规则遮挡
5. **沙箱的 full/partial 诚实报告 + 绝不静默降级** —— 这是安全工程的态度问题

### 6.3 明确不抄的三条

1. **4 层 YAML patch 合成** —— 配置组合面指数增长，大团队能吸收，小团队不能
2. **60+ 接缝铺开** —— 每个都是永久承诺；贡献点可数是可编译期切掉插件系统的前提
3. **可替换的沙箱与可替换的主循环** —— 见原则 2、3 与 §5

### 6.4 我们已经更强的五条

1. 安装期披露（模型可见文本必须过人眼，超限拒绝安装而非警告）
2. 权限规则的来源优先级与按来源整批撤销
3. 决策理由的可审计枚举
4. 插件子系统可编译期完全移除，并由构建脚本断言依赖图
5. MCP 的进程内注册（宿主可直接注入 client，无子进程无 socket）

**这五条应当写进对外文档的第一屏。** 它们是「更适合被信任地二开」的实质证据，而不是宣传语。

## 7. 现状差距盘点

按 §3 总表统计：

| 状态 | 数量 | 说明 |
|---|---|---|
| ✅ 已具备 | ~24 | 主要集中在模型、工具实现、场景、权限、分发 |
| ⚠️ 部分具备 / 形同虚设 | ~17 | trait 存在但唯一实现、或被热路径绕过、或只收具体类型 |
| ❌ 缺失 | ~18 | 集中在执行层、记忆、提示词装配、宿主集成 |
| 🔒 刻意不开 | 11 | 符合目标设计 |

三类典型问题，按危害排序：

**问题 1 · 形同虚设的 trait。** 抽象存在但没有第二实现、且被具体调用绕过。危害在于**它让人以为可以扩展**，二开者按 trait 写了实现，发现热路径根本不走它。典型：压缩策略（触发逻辑在循环里，多数策略直接调具体函数）、持久化（唯一实现且 trait 文档自述如此）、工具注册表（Builder 只收具体类型，第二实现根本接不上）。

**问题 2 · 中心域完全没有抽象。** 执行层、记忆、事件出口、消息投影。二开者要动只能 fork。

**问题 3 · 地图与实物不符。** 对外文档描述的扩展面与代码不一致（注入方法名与签名、事件数量、传输方式数量、协议实现状态、模块清单），而**入口目录的命名过度承诺**——名为「外部接口」的目录里有不含任何 trait 的模块，而两个真正的扩展点却在目录之外。

> **问题 3 的修复成本最低、感知最直接。** 想二开的人第一眼看到的就是这两样东西，它们现在都在误导。这应当排在所有代码改动之前。

## 8. 迁移策略

原则：**每阶段独立可交付、可止损；先让契约就位，再让实现跟上。** 不做大爆炸式重构。

### 阶段 0 · 地图对齐（零风险，先做）

- 对外文档与代码对齐：注入方法的真实签名、事件与传输方式的真实数量、协议实现的真实状态、模块清单
- **补上插件执行模型的说明**——完整的组件模型插件系统、默认为空的能力声明、安装期披露，这些目前一个字都没讲
- 重整「外部接口」目录：只放真正的扩展契约，把不含 trait 的模块移走，把在目录外的扩展点移进来
- 产出一份**扩展点索引**（即 §3 总表），作为二开者的入口

**验收**：一个陌生人只读文档，能正确说出「我要换 X，该实现哪个 trait / 注册什么 / 配置哪一项」。

### 阶段 1 · 契约就位（不改行为）

只动签名和形状，行为保持不变，默认实现即现有实现。

| 项 | 动作 | 破坏性 |
|---|---|---|
| T2 | 注册表 trait 补 `register/replace/remove`，返回 disposer；Builder 收 trait 对象而非具体类型 | 小（旧方法保留一版） |
| H1 | 新增事件出口 trait，现有 channel 实现成默认 sink | 无 |
| H2 | 人机询问收敛为单一 trait，默认实现为「拒绝」 | 小 |
| S1 | 持久化 trait 去掉泄漏格式的措辞，补第二实现（内存版即可）验证契约 | 无 |
| S2 | 日志增加扩展事件变体 + 未知命名空间可跳过 | 无（加变体） |
| M2 | provider 构造改为工厂注册表 | 无 |
| M7 | token 计数抽 trait | 无 |
| M9 | 凭据获取抽 trait，默认仍读配置 | 无 |
| — | 修复权限接口收具体注册表类型的泄漏 | 小 |

**验收**：能在不改内核代码的前提下，用一个外部 crate 换掉持久化后端、接管事件流、注册一个新的模型协议。

**止损点**：若阶段 1 之后仍没有任何外部实现出现（包括自己写的第二实现），说明契约画得不对，先停下来找原因，不要进阶段 2。

### 阶段 2 · 点位体系与贡献注册（二开能力的主体）

这一阶段交付「**在各个环节写自己的提示词与工具**」这个核心诉求。

| 项 | 动作 |
|---|---|
| P1–P4 | 提示词从「一次性返回」改为「注册 + 装配点位」，块具名、有来源、可撤销 |
| T5 | 工具环绕点位 |
| T7 | 结果变换器从循环里提出来 |
| L2 | 点位清单成体系：明确每个点位的时机、可改写范围、频次分级、按信任级授予 |
| S4 | 追加拦截（只读） |
| D2 | 插件装载契约支持第二载体；**脚本载体落地**（见下） |
| M4/M5 | 请求与消息拦截 |
| M6 | 流式拦截：默认不暴露逐 chunk 点位，只给完整消息与完整工具调用；需要时提供声明式规则；显式 opt-in 的逐 chunk 脚本计入配额 |
| R1–R4 | 记忆抽 trait + 检索器 + 点位 |
| L3 | 子 agent 派生补第二实现 |

**关于脚本载体**：现有的点位后端里，最便宜的一档是缺失的——要在点位上做一点轻活，现在只能付一个子进程或一次模型调用的代价。补一个进程内脚本后端（µs 级、可有状态、可热改、可改提示词），是这一阶段成本最低、收益最高的一项。它与 wasm 载体不是替代关系：**wasm 承载下载来的工具，脚本承载自写的编排**，两者的信任级和变更频率本就不同。详见后续的插件开发文档。

**验收**：不改内核、不重编译，能用一份脚本 + 一份配置，实现「在某个环节插入自己的提示词、调用自己的工具、并按自己的规则决定是否继续」。

### 阶段 3 · 决策外移（让中心可调而不失控）

| 项 | 动作 |
|---|---|
| L1 | 轮次策略 trait：停止条件、退避、重试、压缩时机从循环里提出来，骨架不动 |
| C1–C3 | 压缩策略真正接管触发与全部策略，热路径不再绕过 trait |
| M8 | 退避与降级策略并入轮次策略 |
| S3 | 日志→消息投影抽 trait |
| S5/S6 | 查询索引与大对象外置 |
| P8 | 装配器整体替换（少用，但补齐） |
| K1/K3 | 技能与指令来源抽 trait |
| H4–H6 | 时钟/随机/环境、配置来源、生命周期 |

**验收**：能用一个策略实现改变「跑几步停、失败怎么退、什么时候压缩」，而不触碰循环代码；确定性重放可以通过替换时钟与随机源实现。

### 阶段 4 · 执行层抽象（大工程，单独立项）

四个 trait 一组落地，所有涉及系统调用的内建工具改为通过它们工作；沙箱后端收敛为单一契约并补上诚实报告。

**这一步是「换一个 provider，把 Bash、PTY、文件、LSP 整体搬到容器或远端」的前提**，也是这个内核在商业上最有价值的一条能力。但它要动全部内建工具，必须单独立项，不要和阶段 1–3 混做。

**验收**：存在至少两个执行层 provider（本地 + 一个远端或容器），切换只改配置。

### 迁移期的兼容策略

- **加，不改**：新 trait 先以默认实现落地，旧接口保留一个版本周期并标注废弃
- **契约先于实现**：每个新 trait 落地时至少有两个实现（真实现 + 内存/假实现），否则等于没验证
- **每阶段一个外部验证者**：用一个真实的外部使用场景验收，不靠内部自测。没有外部验证者的阶段不算完成

## 9. 不做清单

写在这里是为了在未来每一次诱惑面前有据可依。

- ❌ **不把沙箱、权限求值顺序、能力授权做成可插拔**（§5）
- ❌ **不做 4 层配置合成**
- ❌ **不把接缝数量铺开到几十个**——每一个都是永久承诺
- ❌ **不把主循环做成可替换实现**——只开放决策（L1）
- ❌ **不做场景合成/继承**
- ❌ **不让插件自称安全**——并发安全、只读等声明只用于调度，永不用于放宽权限
- ❌ **不给下载来的插件改写工具入参与删除内核提示块的能力**
- ❌ **不在高频路径（流式 chunk）默认暴露脚本点位**

## 附录 A · 术语

| 术语 | 含义 |
|---|---|
| **扩展点** | 内核对外承诺的可扩展位置，四种形态之一（A/B/C/D） |
| **接缝（seam）** | 特指 A 型扩展点：一个契约 + 若干实现 + 若干消费者。三者齐备才算接缝，只有契约不算 |
| **点位（hook point）** | 特指 C 型扩展点：流程中的一个可观察/可否决/可改写的时刻 |
| **贡献（contribution）** | 特指 B 型：向注册表添加条目，返回可撤销句柄 |
| **载体** | 扩展代码的执行形式：Rust 原生 / wasm 组件 / JS 脚本 / 纯配置 |
| **信任级** | 内核（宿主编译期注入）/ 自写（用户脚本）/ 下载（第三方） |
| **披露** | 安装时把插件的模型可见文本呈现给人审阅，超限拒绝安装 |
